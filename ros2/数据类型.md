本文介绍 ROS 2 中常用的标准消息类型。这些消息来自 `common_interfaces` 仓库，不是 ROS 2 核心代码。

# 一、std_msgs::msg::Header

ROS2 中，`std_msgs/Header` 是几乎所有“带时间戳 / 坐标系的”消息都会带的元数据头。定义如下：
```text
# std_msgs/msg/Header.msg
builtin_interfaces/Time stamp
string frame_id

# builtin_interfaces/msg/Time.msg
int32 sec       # 可以取负值
uint32 nanosec  # 范围 [0, 1e9)，负时间用"向负无穷取整"表示，如 -1.7s = {sec:-2, nanosec:3e8}
```
注意两点：
- **它是“采集时刻”，不是“发送时刻”**：多传感器融合时靠这个时间戳对齐数据；如果用发送时间，会引入通信延迟误差。
- **零值 `{0, 0}` 表示“未指定 / 未知”**：很多消费方（如 `message_filters`）会跳过它，或者替换成当前时间。

# 一、`sensor_msgs::msg`

## 1. JointState

`JointState` 消息同时包含关节空间的位姿、速度、力。

### 消息定义

```text
# sensor_msgs/msg/JointState.msg

std_msgs/Header header

string[]  name
float64[] position   # q
float64[] velocity   # q̇
float64[] effort     # τ
```

字段说明下如

| 字段 | 类型 | 含义 | 单位 |
| --- | --- | --- | --- |
| `header` | `std_msgs/Header` | `stamp`：采集时刻；`frame_id`：通常为空 | — |
| `name` | `string[]` | 关节名，唯一标识每个关节 | — |
| `position` | `float64[]` | 关节位置 | 转动关节 rad，移动关节 m |
| `velocity` | `float64[]` | 关节速度 | rad/s 或 m/s |
| `effort` | `float64[]` | 关节力矩 / 力 | N·m 或 N |如如下

其中：
- 所有数组长度必须相同，或者为空。只有这样才能把 `name[i]` 和 `position[i]` / `velocity[i]` / `effort[i]` 对应起来。
- 每个字段都是可选的，例如没有力矩传感器时，`effort` 可以为空。
- 一条消息里的所有关节状态必须同一时刻采集，因此只有一个 `header.stamp`，而不是每个关节一个时间戳。

## 三、`geometry_msgs::msg`

### 1. PoseStamped

`PoseStamped` 包含笛卡尔空间的位置 / 位姿数据：位置 + 四元数姿态，表示末端在哪、朝哪。

#### 消息定义

```text
# geometry_msgs/msg/PoseStamped.msg
std_msgs/Header header
Pose pose

# geometry_msgs/msg/Point.msg
# This contains the position of a point in free space
float64 x
float64 y
float64 z

# geometry_msgs/msg/Quaternion.msg
# This represents an orientation in free space in quaternion form.
float64 x 0
float64 y 0
float64 z 0
float64 w 1
```

#### 字段语义

| 字段 | 含义 | 单位 / 约定 |
| --- | --- | --- |
| `header.stamp` | 位姿对应的时刻 | 采集时刻，非发送时刻 |
| `header.frame_id` | 位姿所相对的参考坐标系 | TF frame 名，如 `base_link`，不加前导 `/` |
| `pose.position.x/y/z` | 目标坐标系原点在 `frame_id` 下的位置 | m |
| `pose.orientation.x/y/z/w` | 姿态四元数 | 单位四元数，顺序是 x, y, z, w（标量 w 在最后） |

#### 关键约定

- 位置和姿态是同一个坐标系下的：`position` 是被表达物体原点在 `frame_id` 中的坐标，`orientation` 是它自身坐标轴相对 `frame_id` 的旋转。两者共同定义了一个完整的刚体变换。
- 四元数必须归一化，否则旋转矩阵会带缩放；$q$ 和 $-q$ 表示同一个旋转。
- `w` 在最后（ROS 惯例）；Eigen 的构造函数是 `Quaterniond(w, x, y, z)`，顺序不同——这是最常见的 bug 来源。
- `(0, 0, 0, 0)` 不是合法四元数；默认值 `(0, 0, 0, 1)` 是单位旋转。
- 空的 `frame_id` 意味着“未指定坐标系”，消费方只能按默认约定猜测。

### 2. TwistStamped

`TwistStamped` 包含笛卡尔空间的线速度、角速度数据，表示末端动多快。

#### 消息定义

```text
# geometry_msgs/msg/TwistStamped.msg
std_msgs/Header header
Twist twist

# geometry_msgs/msg/Twist.msg
Vector3 linear
Vector3 angular

# geometry_msgs/msg/Vector3.msg
float64 x
float64 y
float64 z
```

#### 字段语义

| 字段 | 含义 | 单位 |
| --- | --- | --- |
| `header.stamp` | 速度对应的时刻 | — |
| `header.frame_id` | 线速度 / 角速度表达所在的坐标系 | TF frame 名 |
| `twist.linear.x/y/z` | 线速度矢量 | m/s |
| `twist.angular.x/y/z` | 角速度矢量 | rad/s |

#### 物理含义

- `linear` 是某个点的速度，但消息里没有写明是哪个点，只能靠约定。通常理解为“该刚体坐标系原点”或“TCP 点”的速度。
- `angular` 是自由矢量，与参考点无关。方向是转轴（右手定则），模长是角速率。同一刚体的角速度在任何平移后的坐标系里都是同一个矢量（只有分量在不同旋转坐标系下不同）。
- 所以 `Twist` 描述刚体运动需要“一个点 + 角速度”，但消息里没有参考点字段——这是 ROS 历史设计上的一个空缺。

#### frame_id 的约定（最大的坑）

`TwistStamped` 只有一个 `frame_id`，无法区分“以哪个坐标系观察”和“观察哪个坐标系”。实践中存在两种理解：

| 理解 | 含义 |
| --- | --- |
| 空间速度（spatial twist） | 速度矢量在 `frame_id` 下表达，参考点是该系原点 |
| 物体速度（body twist） | 速度是刚体相对 `frame_id` 的运动，但分量在刚体自身系下表达 |

### 3. WrenchStamped

`WrenchStamped` 包含笛卡尔空间的力、力矩数据，表示末端受多大力 / 力矩。

#### 消息定义

```text
# geometry_msgs/msg/WrenchStamped.msg
std_msgs/Header header
Wrench wrench

# geometry_msgs/msg/Wrench.msg
Vector3 force
Vector3 torque

# geometry_msgs/msg/Vector3.msg
float64 x
float64 y
float64 z
```

#### 字段语义

| 字段 | 含义 | 单位 |
| --- | --- | --- |
| `header.stamp` | 力 / 力矩对应的时刻 | — |
| `header.frame_id` | 力和力矩表达所在的坐标系 | TF frame 名 |
| `wrench.force.x/y/z` | 力矢量 | N |
| `wrench.torque.x/y/z` | 力矩矢量 | N·m |

#### 物理含义

- 一个 wrench（力旋量）由力 + 力矩组成，是刚体静力学 / 动力学的 6 维广义力，与 `Twist`（6 维广义速度）互为功共轭对偶：瞬时功率 $P = F \cdot v + \tau \cdot \omega$。
- `force` 是自由矢量，与参考点无关。
- `torque` 是关于某个参考点的力矩，依赖参考点。参考点平移 $r$ 后：$\tau' = \tau + r \times F$。
- 消息里没有参考点字段，和 `Twist` 一样，只能靠约定——通常理解为“坐标系 `frame_id` 的原点”。所以“力矩的数值”一旦脱离坐标系和参考点，就无从解释。
- **`frame_id` 决定分量表达**：力和力矩的分量是在 `frame_id` 下表达的。UR 的 `getActualTCPForce()` 返回的是 TCP 坐标系下的力 / 力矩；若要换到基坐标系，力只需 $F_{\text{base}} = R_{\text{base\_tcp}} \cdot F_{\text{tcp}}$（只旋转、不平移），力矩还要考虑参考点变化。

#### 几个容易踩的坑

- **力矩依赖参考点**：同一个力作用在不同点，力矩不同；换坐标系时不能只做旋转，还要算力臂 $\tau' = \tau + r \times F$。
- **`frame_id` 为空时语义缺失**：本工程 `tcp_force_.header.frame_id = ""`（`ur_robot.cpp:73`），但数据实际是 TCP 系。下游若当它是基座系，方向会完全错。
- **符号约定**：UR 的 `getActualTCPForce()` 表示“作用在工具上的力”。如果你的控制律里需要“工具施加给环境的力”，就要取反。不同传感器（ATI、宇立）的符号约定也不同，接入前必须标定确认。
- **零漂 / 重力补偿**：raw wrench 里含有工具自身重力，力控前通常要 `zeroFtSensor()`（代码在 `ur_robot.cpp:75` 调了一次）或做重力补偿，否则空载也有读数。
- **力 / 力矩量纲不同**：做阈值判断时不要用同一个 scale；`force_limits` 是 6 维的，可以分别设 N 和 N·m 的上限。
- **高频噪声**：wrench 是差分 / 应变片信号，直接用于导纳控制前一般要低通滤波（一阶或 Butterworth），否则会把噪声积分成抖动。

## 四、物理上的成对关系

- **Pose vs Twist**：位姿是位置，速度是位姿的一阶导数，二者共同描述运动学状态。
- **Twist vs Wrench**：在功率意义上互为对偶，瞬时功率 $P = F \cdot v + \tau \cdot \omega$。所以控制里常把它们配对使用：阻抗 / 导纳控制就是“检测到 `Wrench`，产生 `Pose` / `Twist` 的修正”。

```mermaid

    P["PoseStamped<br/>位姿"] -->|"一阶导数"| T["TwistStamped<br/>速度"]
    T ---|"功率对偶<br/>P = F·v + τ·ω"| W["WrenchStamped<br/>力 / 力矩"]
```

## 六、几个实际使用中的关键差异

### JointState：变长 + 按名字索引

`position[0]` 不一定是第一个关节，必须根据 `name` 来匹配。本工程是自己发布、自己订阅，`name` 固定为 `joint_names_` 参数，所以直接按顺序取用；若接入别人发布的 `joint_state_broadcaster`，就要做 `name → index` 映射。另外，四个数组可能为空（比如没有力矩传感器时 `effort` 为空），消费方在使用前必须判断长度。

### PoseStamped：四元数要转旋转向量

`PoseStamped` 的姿态是四元数，而 UR 需要的是旋转向量。`servoL` 需要 `[x, y, z, rx, ry, rz]`，所以 `poseOrientationToRotationVector()` 做了 `四元数 → AngleAxis → axis * angle`。这也是 `PoseStamped` 和 `JointState` 用法差别的典型体现：一个要进行坐标变换或旋转变换，另一个是直接使用关节值。

### TwistStamped：参考系最容易搞错

线速度和角速度必须明确“在哪个坐标系下表达”。同一个运动，在 `base` 系和 `TCP` 系下数值完全不同。ROS 2 的 `Twist` 没有显式的 child frame，只能靠 `header.frame_id` 和约定说明——UR 的 `getActualTCPSpeed()` 返回的是基坐标系下的 TCP 速度（这一点常被误解为 TCP 系）。

### WrenchStamped：坐标系更微妙

力是“在某个坐标系下表达的矢量”，UR 的 `getActualTCPForce()` 给出的是 TCP 坐标系下的力和力矩。要换到基坐标系，得做：

$$F_{\text{base}} = R_{\text{base\_tcp}} \cdot F_{\text{tcp}}$$

力矩还要考虑力臂：

$$\tau_{\text{base}} = R \cdot \tau_{\text{tcp}} + p \times F$$

本工程 `frame_id` 全是空串（`ur_robot.cpp:70-73`）。下游如果混用 pose（`base` 系）和 wrench（`TCP` 系），就会算错，建议补上 `frame_id`。

### JointState：不叫 Stamped，但也带 header

它照样有 `stamp`（状态采集时刻）和 `frame_id`（通常为空）。时间戳对齐对多传感器融合很重要——本工程在 `ur_robot.cpp:95` 统一打了时间戳。

### 力控：Wrench 的作用轴由 selection_vector_ 决定

`forceMode(task_frame_, selection_vector_, wrench_, force_type_, force_limits_)` 中，只有 selection vector 置 1 的轴才会用力指令，其余轴仍按位置控制——所以一个 `WrenchStamped` 并不是“六个自由度都出力”。

> **串起来**：前三个描述运动，最后一个描述作用力；`JointState` 与笛卡尔三件套之间靠雅可比 $J$ 相互转换：$\dot{x} = J\dot{q}$，$\tau = J^{T}F$。
